## 4. As formas de escrever macro — enumeradas e testadas

Cada forma num módulo próprio, compilada sob `-w3 -es2` e com o dump lido.

| forma | compila | `usesMacro` | nó `MACRO` |
|---|---|---|---|
| `&cN` | ✅ | ✅ | `val=<VAR>` |
| `&cN.` (ponto terminador) | ✅ | ✅ | `val=<VAR>` |
| `&cN := 9` (alvo de atribuição) | ✅ | ✅ | `val=<VAR>` |
| `&cF()` (chamada) | ✅ | ✅ | `val=<VAR>` |
| `M->&cN` (memvar aliased) | ✅ | ✅ | `val=<VAR>` |
| `FIELD->&cN` | ✅ | ✅ | `val=<VAR>` |
| `&cN[ 1 ]` (índice) | ✅ | ✅ | `val=<VAR>` |
| `o:&cF` (send) | ✅ | ✅ | `val=<VAR>` |
| `o:&cF := 1` (send-escrita) | ✅ | ✅ | `val=<VAR>` |
| `{\| \| &cN }` (dentro de codeblock) | ✅ | ✅ | `val=<VAR>` |
| `&( cN )` | ✅ | ✅ | `expr:LIST` |
| `&( cN + "" )` (expressão montada) | ✅ | ✅ | `expr:LIST` |
| `&( cF )()` | ✅ | ✅ | `expr:LIST` |
| `&( "mTot" )` (**literal**) | ✅ | ✅ | `expr:LIST` |
| `&"mTot"` (literal sem parênteses) | ❌ **E0030** | — | — |
| `Eval( &( "{\|\| mTot }" ) )` (bloco por macro) | ✅ | ✅ | `expr:LIST` |
| `Eval( &cB )` / `Eval( &( cB ) )` (bloco de variável) | ✅ | ✅ | `val=<VAR>` / `expr:LIST` |
| `Eval( &( "{\|x\| x + mTot }" ), 1 )` (com parâmetro) | ✅ | ✅ | `expr:LIST` |
| **`__mvGet( "mTot" )`** | ✅ | ❌ **False** | **nenhum** |
| **`Type( "mTot" )`** | ✅ | ❌ **False** | **nenhum** |
| **`Eval( hb_macroBlock( "mTot" ) )`** | ✅ | ❌ **False** | **nenhum** (só `calls[] = HB_MACROBLOCK`) |
| **`Eval( hb_macroBlock( cN ) )`** | ✅ | ❌ **False** | **nenhum** (só `calls[] = HB_MACROBLOCK`) |

**Três conclusões, e a terceira muda a P22:**

1. **Toda forma com `&` produz exatamente UM nó `MACRO` e liga `usesMacro`** — 14 de 14. O
   compilador é consistente: a macro é nó de primeira classe, não buraco opaco.
2. **Duas formas de operando:** `val=<VAR>` (o texto só existe em runtime) e `expr:LIST` (o
   operando é expressão — inclusive constante, como `&( "mTot" )`). Só o segundo caso PODERIA
   ter AST em tempo de compilação, e mesmo assim o compilador **não o dobra**: mantém o nó e
   deixa para o runtime.
3. **Existe uma TERCEIRA família, e ela é a perigosa: chamada por nome via função da RTL.**
   `__mvGet( "x" )`, `Type( "x" )` e **`hb_macroBlock( ... )`** fazem exatamente o que a macro
   faz — alcançam um símbolo pelo nome — e **não acendem `usesMacro` nem produzem nó `MACRO`**.
   São chamadas de função comuns; o único rastro é `calls[].sym`. O `hb_macroBlock` é o mais
   grave dos três: é o jeito **moderno** de montar um codeblock a partir de string, e é o que
   engine de relatório e de browse usa o tempo todo. *(Achado porque o Diego perguntou pelo
   `Eval` de bloco de macro, que a primeira rodada não cobriu.)*

   É esta família que a heurística de string segura hoje.

**A ordem do Diego fecha o desenho (2026-07-27):** *"heurística é code smell e deve ser retirada
mesmo. se houver forma de resolver através de alterações no core, aí sim, senão, o hbrefactor
simplesmente não vai suportar. me recuso a ter heurística nele."*

- O casamento de string **morre incondicionalmente**. Perder o caso é aceitável; ter heurística
  não é. *(Eu havia proposto o contrário — "matar só se houver substituto". Errado.)*
- **Uma lista de `__mvGet`/`Type`/`hb_macroBlock` dentro do `src/hbrefactor.prg` seria a mesma
  heurística com roupa melhor** — conhecimento nosso sobre a RTL, não fato dela.
- **O core tem a casa desse fato, e foi sondada:** `s_stdFunc` em `src/compiler/hbfunchk.c`,
  tabela das funções conhecidas da RTL (67 entradas, nome + aridade), usada para checagem de
  argumentos — e **`TYPE` já está nela**. O caminho é estender `HB_FUNCINFO` com *"alcança
  símbolo pelo nome, no argumento N"*, preencher para a família, e o dump publicar por chamada.
  Quem sabe isso é a RTL. De quebra o compilador ganha o aviso de acesso por nome, que é
  armadilha real com `-gh`.
- **Se a extensão for recusada no upstream:** o hbrefactor não suporta o caso, e diz isso.
- A lista dos três **não está completa** (faltam ao menos `__mvPut`, `hb_macroCompile`, `Do()`,
  `MemVarBlock`/`FieldBlock`) — completá-la é varredura da API do core (§1.3), nunca chute, e é
  item próprio deste backlog.

## 5. AST de macro — o que a sondagem exploratória achou

*(pergunta do Diego: "será que dá pra gerar ast de macros? e como isso funciona junto com
código normal que usa macros?")*

- O binário `harbour` carrega só o **seu próprio** tratamento de nó de macro
  (`hb_compExprNewMacro`, os `hb_p_macro*`). O compilador de macro de verdade
  (`hb_macroCompile`) mora na **VM/RTL**, não nele. Gerar AST de macro em tempo de compilação
  **não é uma flag: é decisão de arquitetura** do binário do compilador.
- Para o operando `val=<VAR>`, **nenhuma arquitetura resolve**: o texto não existe até a
  execução. O fato honesto é o buraco em si, e ele já está publicado (`usesMacro` + o nó
  `MACRO` posicionado + qual expressão o alimenta).
- Para o operando constante, o texto existe — e o caminho §1 seria **usar ferramenta do core
  como oráculo** (compilar um módulo-sonda e ler o dump), não estender o compilador. **Falta
  medir se vale**: não sei a frequência dessa forma em código real, e os greps que tentei
  saíram não confiáveis. *Medir antes de investir (§1.7/2).*
- **Composição com o código normal:** o nó `MACRO` já está posicionado na árvore, então uma
  AST de macro penduraria como **subárvore naquele nó**. Mas o valor seria de **RELATO**, nunca
  de edição: o texto mora numa string, e §1 proíbe editar o não-verificável.

**O caso 73 escondia uma capacidade real dentro da heurística.** O token da string carrega

E o fato entrega **melhor** que a heurística entregava: ela apontava a string, ele aponta
**9:10, o token escrito** — o lugar que uma edição precisa tocar.

**A lição, que vale para o resto da fase:** ao matar uma heurística, cada caso que cai junto
tem de ser interrogado — *o que ele provava tem fato por trás?* Dois dos três eram mesmo da
heurística; o terceiro era uma capacidade legítima entregue pelo canal errado.

### 5b.1 Duas correções que o Diego pegou no desenho da recusa

**(i) O código de recusa não se batiza pela saída.** Eu propus `macro-reach-requires-force`, e
ele apontou que `textual-refs-require-force` — o que já existia — *"pelo nome parece que isso é
heurística ainda"*. Está certo: **código batizado pelo contorno sobrevive à morte da causa**. O
`reason` diz o que É; o `action` diz o que FAZER. A taxonomia ficou:

| fato | quando | ação |
|---|---|---|
| `symbol-named-in-macro` | o core **provou** o nome que a macro resolve | edite a string você mesmo (§1) |
| `macro-target-unknown` | o operando vem de run time — nem o core sabe | confira os sítios e confirme |
| `symbol-in-hbx-export` | linha `DYNAMIC <nome>` na lista de exports | regenere o `.hbx` |

**(ii) O meu fixture afirmava uma quebra que não existia.** Eu montei o caso com `? &cFn`
(macro NU) e escrevi que o rename quebrava o programa. **Medido em run time: falso.** `&cFn`
procura uma **VARIÁVEL** com aquele nome — `Variable does not exist` —, nunca a função. O
programa já estava quebrado antes do rename; eu construí um veredito sobre uma premissa que
não conferi.

As formas que de fato chamam a função, todas medidas rodando: `&cFn.()`, `&( cFn )()`,
`&( cFn + "()" )` e `Eval( hb_macroBlock( cFn + "()" ) )`.

**(iii) O recorte por POSIÇÃO NA ÁRVORE que eu propus em seguida também estava errado, e o
Diego o derrubou na mesma hora** — *"será que está dando muito valor à macro interpretada
diretamente em texto e pouca atenção às outras tantas formas?"*.

Eu havia proposto: função → só macro em posição de chamada; memvar/public → só posição de
valor; `LOCAL` → nenhuma. A base era o dump distinguir `&cFn` (sob `ARGLIST.items`) de
`&cFn.()` (o `fun` de um `FUNCALL`) — o que é verdade, **e irrelevante**:

```
&( cFn + "()" )   ->  MACRO em posicao de VALOR (ARGLIST.items)
runtime           ->  "CHAMOU A FUNCAO"
```

Os parênteses são parte do **texto da macro**, não da sintaxe ao redor. A posição na árvore diz
o que o nó produz **ali**; não diz o que o texto faz. E `hb_macroBlock` vai além: compila um
**codeblock inteiro**, com referências arbitrárias de qualquer espécie — sem nem acender
`usesMacro`.

**A raiz do meu erro:** eu tratei todas as formas como variações de `&nome` (nome nu), quando
`&( expr )`, `&( cVar )()` e `hb_macroBlock` compilam **Harbour arbitrário**. Dei peso demais à
forma mais simples e li as outras através dela.

**A regra honesta é mais curta e mais larga:**

| símbolo renomeado | macro alcança? |
|---|---|
| `LOCAL` / static-local | **NÃO** — provado em run time (`Variable does not exist`) |
| função, memvar/public/private, field, método/DATA | **SIM, qualquer macro de texto desconhecido** |

Ou seja: o recorte real é só o do `LOCAL`. Para nome global, **qualquer** avaliação de macro
cujo texto não seja provado é alcance não-refutável — e é por isso que a recusa carrega a LISTA
dos sítios (medido: 10 avaliações em 264 funções do corpus; curta o bastante para o programador
conferir).

### 5b.2 E então o Diego encerrou o assunto: MACRO ESTÁ FORA DE ESCOPO

*(2026-07-27)*: *"é sabido que macros são runtime, e não dá para controlar — não com o
conhecimento atual que tenho do compilador. deixo para uma fase de pesquisa avançada. (...)
tem que assumir que macros estão fora do nosso controle totalmente ao menos por enquanto."*
E a analogia que fecha: **o Harbour compila código novo em run time e o usa no instante
seguinte** — nenhuma ferramenta de refatoração controla isso.

**Consequência:** as três correções acima (nome do código, fixture errado, recorte por posição)
eram todas sobre um **veredito que não vai existir**. Elas ficam registradas porque as lições
valem — batizar código pelo contorno, afirmar quebra sem medir, usar dado real para responder
pergunta que ele não responde —, mas o desenho que elas corrigiam foi **desmontado**:

- o caso `refuse-rename-macro-may-name-symbol` foi **removido** (travava veredito inexistente);
- **não** há recusa por alcance de macro;
- **memvar** entra na mesma sentença: *"memvar é um code smell; é aceitável que sejamos
  limitados também no tratamento dela"*.

**O que fica no lugar é uma limitação DECLARADA** ([P23](roadmap.md)): `verified` quer dizer
*"verificado contra o que a compilação enxerga"* — o que é escopo, não mentira, **desde que
esteja escrito onde o usuário lê**. Enquanto não estiver, a palavra promete demais. Por isso a
P23 é fase de documentação, e o material da pesquisa futura (operando constante, `s_stdFunc`)
fica registrado lá sem virar compromisso.

### 5c. P23 fechada — e o portão que faltava

A fronteira ficou escrita nos três artefatos que o usuário lê. O trabalho revelou que **dois
deles ensinavam o comportamento recém-removido como virtude**:

- `docs/manual.md` mostrava `possible reference in string` sobre um **`LOCAL`** — que macro
  provadamente não alcança — e o apresentava como *"a disciplina que faz os outros dois
  valerem a pena: saber quando não dizer nada"*;
- `site/index.html` ia além: uma seção inteira (*"Knowing when to stop — a string that is
  really a call"*) terminava em **"hbrefactor is the only one of the three that tells you the
  line is there"**. No instante em que a heurística morreu, isso virou propaganda de uma
  proteção inexistente — e é exatamente a impressão que o Diego identificou como o problema
  de fundo (*"parece estar dizendo que o hbrefactor é bom o suficiente para detectar e evitar
  alterações em código dinâmico"*). Seção e exemplo removidos.

**O achado de processo, que virou [cicatriz §6.5](cicatrizes.md):** eu enumerei os testes
afetados rodando o contrato (`make test`) e reportei três quedas — **faltava a quarta**, e ela
só apareceu por acaso. `site-check` e `lexdiff` estavam **fora** do `make test`. A lei mandava
confiar num contrato que não cobria o portão das afirmações do usuário. Agora cobre, e **antes
do `gotest`**, porque a cadeia para no primeiro erro e os vermelhos de TDD desta fase
emudeceriam justamente os portões recém-trazidos.

**E a formulação que ficou**, aprovada pelo Diego e replicada nos três:

> A ferramenta **refuse onde não vê** — macro cujo alvo só existe em run time é buraco no
> alcance, e o comando para. E **relata onde vê** — quando o compilador diz que uma string
> re-expande um nome. Esse segundo caso é **uma forma entre muitas**: codeblock montado de
> texto, chamada por nome via runtime, nome montado em pedaços — nada disso é visto, e nada
> disso pode ser. **Nenhuma saída desta ferramenta deve ser lida como "seu código dinâmico
> está coberto."** *verified* significa verificado contra o que a compilação enxerga.
